# Inception

## Description

Inception is a system-administration project: it builds a small web infrastructure out of
Docker containers, all orchestrated by Docker Compose and running inside a virtual machine.

The stack serves a WordPress site over HTTPS at `https://rookuma.42.fr`:

```
                 host / VM
   browser ──443/TLS──▶ ┌────────┐   fastcgi :9000   ┌───────────┐   sql :3306   ┌─────────┐
                        │ nginx  │ ────────────────▶ │ wordpress │ ────────────▶ │ mariadb │
                        └────────┘                   │ + php-fpm │               └─────────┘
                            │                        └───────────┘                    │
                            └──── wordpress_data ─────────┘              mariadb_data ─┘
                                 (/home/rookuma/data/wordpress)   (/home/rookuma/data/mariadb)
                        └──────────────── docker network "inception" ────────────────┘
```

- **nginx**: the only entry point, listening on port 443 with TLSv1.2/TLSv1.3 only.
- **wordpress**: WordPress + php-fpm (no web server), installed and configured with WP-CLI.
- **mariadb**: the database server (no web server).
- Two named volumes (database files, website files) whose data lives in `/home/rookuma/data`.
- A dedicated bridge network; only nginx publishes a port.

## Instructions

Requirements: a Linux VM with Docker Engine, the Docker Compose plugin, `make`, and `sudo`.

```sh
make hosts   # once: adds "127.0.0.1 rookuma.42.fr" to /etc/hosts
make         # generates secrets if missing, creates data dirs, builds and starts everything
```

Then open <https://rookuma.42.fr> (accept the self-signed certificate).
The admin panel is at <https://rookuma.42.fr/wp-admin>.

| Command        | Effect                                                            |
|----------------|-------------------------------------------------------------------|
| `make` / `up`  | Build images and start the stack in the background                |
| `make stop`    | Stop containers (keep them)                                       |
| `make start`   | Restart stopped containers                                        |
| `make down`    | Remove containers and network (data kept)                         |
| `make ps`      | Show container status                                             |
| `make logs`    | Follow the logs of every service                                  |
| `make fclean`  | Remove containers, images, volumes **and** the data on the host   |
| `make re`      | `fclean` + `all`                                                  |

To use another login, edit `LOGIN`, `DOMAIN_NAME` and `DATA_PATH` in `srcs/.env`.
See [USER_DOC.md](USER_DOC.md) and [DEV_DOC.md](DEV_DOC.md) for more details.

## Project description

### Use of Docker and sources in this project

Every service has its own image, written from scratch on top of `debian:bookworm`
(Debian 12, the penultimate stable Debian release). No pre-built service image is pulled.

```
Makefile                         entry point: secrets, data dirs, docker compose
secrets/                         git-ignored, generated by make (Docker secrets)
srcs/.env                        non-confidential configuration (domain, user names…)
srcs/docker-compose.yml          services, named volumes, network, secrets
srcs/requirements/<service>/
    Dockerfile                   image definition
    conf/                        configuration files copied into the image
    tools/entrypoint.sh          first-run setup, then `exec` of the daemon as PID 1
```

Main design choices:

- **One process per container, in the foreground, as PID 1.** Each entrypoint script does its
  one-time setup and then `exec`s `mariadbd`, `php-fpm8.2 --nodaemonize` or
  `nginx -g 'daemon off;'`. No `tail -f`, `sleep infinity` or `while true`: the container lives
  exactly as long as the daemon, so `restart: always` can bring it back after a crash, and
  signals from `docker stop` reach the daemon directly.
- **Idempotent initialisation.** MariaDB is bootstrapped only when the data directory is empty;
  WordPress is copied into the volume, configured and installed only if it isn't already. Restarts
  and rebuilds never wipe data.
- **Secrets generated locally.** `make` creates random passwords in `secrets/` (git-ignored) and
  Compose mounts them in `/run/secrets/`. The Dockerfiles and `.env` contain no password.
- **TLS certificate created at runtime** by the nginx entrypoint, so no private key is baked into
  an image layer.
- **Healthcheck on MariaDB** + `depends_on: condition: service_healthy`, so WordPress only starts
  when the database accepts connections.
- The WordPress administrator is `siteowner` (the entrypoint refuses any admin name containing
  "admin"); a second user, `writer`, has the author role.

### Virtual Machines vs Docker

A virtual machine emulates a whole computer: it boots its own kernel on virtualised hardware,
which gives strong isolation but costs memory, disk and boot time. A Docker container is an
isolated process on the host kernel (namespaces + cgroups) with its own filesystem image: it
starts in milliseconds and is much lighter, at the price of sharing the kernel with the host.
In this project the VM provides the isolated machine, and Docker splits the services inside it.

### Secrets vs Environment Variables

Environment variables are convenient for configuration, but they are visible to every process in
the container, appear in `docker inspect`, and are easily leaked into logs. Docker secrets are
files mounted read-only in `/run/secrets/` at runtime; they do not show up in `docker inspect`
or in image layers. Here, non-sensitive settings (domain, database name, user names) are
environment variables from `srcs/.env`, and every password is a secret.

### Docker Network vs Host Network

With `network_mode: host` a container shares the host's network stack: no isolation, every
listening port is exposed on the host, and ports can collide. A user-defined bridge network gives
the containers a private network with built-in DNS (they reach each other as `mariadb`,
`wordpress`), and only explicitly published ports are reachable from outside. Here only
nginx publishes a port (443); MariaDB (3306) and php-fpm (9000) are internal.

### Docker Volumes vs Bind Mounts

A bind mount maps an arbitrary host path into a container; it depends on the host's directory
layout and is managed outside Docker. A named volume is a Docker-managed object: it has a name,
appears in `docker volume ls`, can be inspected, and is decoupled from the container lifecycle.
This project uses named volumes (`mariadb_data`, `wordpress_data`) created with the `local`
driver, whose `device` option stores their data in `/home/rookuma/data/…` as the subject
requires. They are still volumes, declared in the top-level `volumes:` section and referenced by
name.

### Use of AI

An AI assistant (Claude) was used to draft the first version of the Dockerfiles, entrypoint
scripts, `docker-compose.yml`, Makefile and the documentation files, and to check them against
the subject (TLS versions, PID 1, secrets handling, volume configuration). Every file was then
reviewed, tested (TLS 1.1 rejected / 1.2 and 1.3 accepted, data persistence across `make down`
/ `make up`, automatic restart after a crash) and adjusted by hand.
